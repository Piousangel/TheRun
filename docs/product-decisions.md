## 2026-09-03 — 4자 리뷰(코드·디자인·PM·PO) 이후 오너 결정

리뷰 종합: 코드 리뷰 결함 15건, 제품·디자인·플랫폼 지적 30여 건.
아래는 그중 **오너만 답할 수 있어 리뷰어들이 판단을 미뤘던 6건**에 대한 결정이다.

### D-01. 전술 보드 — **유지하고 제대로 동작하게 만든다**

PM은 삭제를 권고했다(상태 미저장, 선수에게 안 보임, 위젯 534줄 + 5파일이 Phase 5 재작성 대상).
**오너 판정: 전술 보드는 이 제품의 핵심이다. 버리지 않고 실제로 동작하게 디벨롭한다.**

리뷰가 지적한 "무용지물"의 원인은 기능 자체가 아니라 **배선**이었다. 세 가지를 고치면 살아난다.

| 지금 | 고쳐야 할 것 |
|---|---|
| `useTacticalBoardStore`가 persist 없는 세션 스토어 → 새로고침 = 포메이션 소멸 | 포메이션을 서버에 저장. `Match`에 붙이는 것이 자연스럽다 |
| 팀 데이터를 운영자 localStorage에서 읽음 → **선수는 자기 포지션을 영원히 못 봄** | D-04(팀 편성 서버 저장)가 선행 조건. 해결되면 자동으로 풀린다 |
| 드래그 비활성, 10개 고정 슬롯 + 포지션 변경 메뉴 | 모바일에서 실제로 조작 가능한지 재검토(디자이너: 컨텍스트 메뉴가 탭 좌표에 절대 배치돼 뷰포트 이탈 가능) |

**후속 작업:** Phase 3에서 D-04와 **같이** 한다. 순서를 나누면 팀 데이터 소스가 두 번 바뀐다.
**보류:** 전술보드 좌표계·포지션 슬롯·포메이션 프리셋 자체는 그때까지 손대지 않는다(스펙 §4 #14 유지).

### D-02. 멤버 스탯 6종 — **유지한다**

PM은 1축 3단계 태그 + `prefers_gk` + 비공개를 제안했다(정치 유발, 초기 세팅 120슬라이더, 6차원을 단순 합으로 뭉갬).
**오너 판정: 스탯 6종을 유지한다.**

단, PM 지적 중 **스탯 유지와 무관하게 여전히 유효한 두 가지**가 남는다. 이건 별개 항목으로 다룬다.

- **자동 밸런싱이 6차원을 단순 합으로 1차원화한다.** 스피드 90/수비 30과 스피드 60/수비 60이 동일 취급된다. 6개를 입력받는 의미가 여기서 사라진다.
- **밸런싱에 골키퍼 개념이 없다.** 아마추어 풋살에서 팀 균형을 실제로 좌우하는 단일 변수인데 스탯 6종 어디에도 없다. `TeamMatchData.goalkeeper_id`는 이미 있으므로 밸런싱 입력으로 쓸 수 있다.

**후속 작업:** 밸런싱 알고리즘 개선은 Phase 3 백로그. 스탯 스키마는 건드리지 않는다.
**미결:** 스탯 공개 범위(전원 공개 유지 여부)는 이번에 결정되지 않았다. 현행(전원 공개) 유지.

### D-03. 휴대폰 번호 — **PO 권고를 수용한다 (도메인에서 제거)**

원래 용도인 계정 연결 대조가 기존 마이그레이션(`20260312_mask_member_numbers_...`)에서 이미 제거됐고, 연락은 단톡방에서 한다. 현재 `getMemberPhoneDisplay`는 마스킹 함수가 아니라 센티넬 값(`000-0000-0000`)일 때만 다른 문구를 보여주는 함수이고, 실번호는 전 로그인 사용자에게 평문 노출된다.

**결정: `members.phone_number`를 도메인에서 뺀다.** Supabase 프로젝트가 없는 지금이 가장 싸게 지울 수 있는 시점이다.

**후속 작업:** 폼 스키마 3곳(`member-create` / `member-edit` / `account-member-edit`), `getMemberPhoneDisplay`, 멤버 카드·상세·연결 화면의 노출 지점, 시드, 포트/어댑터 타입. 재연결 시 컬럼 DROP 마이그레이션.
**오너 코멘트가 강하지 않았으므로 되돌릴 여지를 남긴다:** 남기기로 바뀌면 별도 테이블 + 관리자 전용 RLS + 뒷 4자리 표시가 대안이다.

### D-04. 팀 편성 — **서버에 저장한다 (승인된 스펙 §4 #4를 뒤집는다)**

스펙 §4 #4는 팀 나누기의 `persist`(localStorage) 유지를 결정해 뒀다. **PM과 디자이너가 독립적으로 그 결정에 이의를 제기했고, 오너가 뒤집기로 판정했다.**

지금 구조의 실제 피해:
- 멤버는 자기 팀을 앱에서 볼 수 없다 → 운영자가 스크린샷을 찍어 단톡방에 올린다
- 집 노트북에서 팀을 짜고 운동장에서 폰으로 열면 **관리자도 팀이 없다는 화면을 본다**
- 로컬 플래그가 `/matches`의 경기 생성 UI 렌더 게이트다 → 루프가 여기서 끊긴다
- 전술 보드가 이 로컬 데이터를 읽는다 → D-01의 근본 원인

**해법(두 리뷰어가 같은 것을 제시):** 팀 편성 확정 = `status: 'pending'` Match 생성.
`Match`가 이미 `team_a.member_ids` / `team_b.member_ids`를 갖고 있어 **새 도메인·새 포트가 필요 없다.**
`team-split-storage`는 "확정 전 초안"에만 쓰고, 확정 시점에 `matches.create()`로 넘긴다.

**함께 고칠 것:** 자동 밸런싱이 투표 참석자가 아니라 전체 멤버를 나눈다(`team-split-auto.tsx`). 입력을 선택된 투표의 참석자로 바꾸는 것은 몇 줄이다.
**후속 작업:** Phase 3. D-01과 같이 한다.

### D-05. 데모 링크를 클럽에 뿌릴 것인가 — **아직 뿌리지 않는다** (오너가 판단 위임)

**판단: 지금은 뿌리지 않는다. Supabase 재연결 이후에 뿌린다.**

근거:
1. 로컬 어댑터는 데이터가 각자 브라우저 IndexedDB에만 있다. **두 명이 각자 투표해도 서로의 응답이 절대 보이지 않는다.** 관리자 화면에는 시드 데이터만 뜬다. 즉 지금 뿌리면 "투표했는데 안 들어갔다"가 **버그가 아니라 정상 동작으로** 발생한다.
2. 작은 조직에서 도구가 죽는 가장 흔한 방식이 이것이다. 한 번 신뢰를 잃으면 서버가 붙은 뒤에도 회복되지 않는다.
3. D-06으로 Supabase 복귀가 확정됐다. 몇 주 기다리면 진짜로 공유되는 앱을 뿌릴 수 있는데, 그 전에 미리보기를 뿌려 첫인상을 소모할 이유가 없다.
4. 지금 데모 URL은 **여는 사람 누구나 클릭 한 번으로 슈퍼관리자**가 된다(`DevRoleSwitcher`). 데모로는 옳은 설계지만 클럽 배포용은 아니다.

**예외 — 이렇게는 지금 보여줘도 된다:** 1:1로, 옆에서 화면을 같이 보면서, "화면 미리보기"라고 명시하고. 링크를 단톡방에 던지는 것과는 다르다.

**뿌리기로 바꿀 경우의 선행 조건:** 앱 셸 상단 상시 배너. `isLocalAdapter()`가 이미 있어 한 줄이면 된다.
> "지금은 **화면 미리보기**입니다. 입력한 내용은 본인 폰에만 저장되고 서로에게 보이지 않습니다. 실제 투표는 아직 단톡방에서 합니다."

핵심은 **"저장된다"고 말하지 않는 것**이다. "데모"라는 단어만으로는 사람들이 "덜 완성된 진짜 앱"으로 읽는다.

### D-06. Supabase — **복귀 확정**

**결정: Supabase로 돌아간다.** 무료 티어 새 프로젝트.

이 결정으로 아래 항목들이 "언젠가"에서 **재연결 차단 조건**으로 승격된다. 상세 절차는 `docs/supabase-reconnect.md`.

| # | 차단 항목 | 무엇이 문제인가 |
|---|---|---|
| 1 | 가입 게이트 | 지금은 **로그인 = 열람 권한**. 구글 계정만 있으면 클럽 명부 전체를 읽는다. 필요한 건 인증이 아니라 인가다 |
| 2 | `db:promote-social-admins` 삭제 | SQL 세미콜론 오타로 첫 문장이 조건 없는 `UPDATE app_profiles SET role='admin'`. psql이 트랜잭션 없이 실행해 **전원 관리자 승격 후 구문 오류로 종료**한다 |
| 3 | 멤버 연결 본인 확인 | 전화번호 대조가 이미 제거됨. 아무 미연결 멤버나 가로챈 뒤 이름·번호를 덮어쓸 수 있다. D-03으로 번호를 빼므로 **관리자 승인 방식**이 답이다 |
| 4 | `get_claimable_members()` 봉인 | `security definer`인데 인증 가드도 `revoke`도 없고, 반환이 `setof members`라 번호·사진·스탯까지 나간다 |
| 5 | `member-photos` 비공개화 | SELECT 정책에 인증 조건이 없어 목록 조회 + 전 파일 다운로드가 가능하다 |
| 6 | 계약 테스트에 권한 축 추가 | 로컬 어댑터에 권한 개념이 없어 QA가 "권한은 괜찮다"는 잘못된 신호를 준다 |

**추가로 반드시 함께 넣을 것 (이번에 프로젝트가 사라진 재발 방지):**
- **keepalive** — GitHub Actions cron으로 주 2회 가벼운 SELECT. 무활동 일시정지 차단
- **주간 백업** — 같은 워크플로에서 `pg_dump` → 아티팩트 보관. 20명치 데이터는 수 MB다

> **복귀 전에 먼저 알아낼 것:** 프로젝트가 사라진 진짜 원인(무활동 정지 / 결제 / 수동 삭제). 원인을 모르면 keepalive가 맞는 처방인지 확신할 수 없다.
> **복구 후 첫 쿼리:** `select role, count(*) from app_profiles group by 1` — 2번 스크립트가 실제로 실행됐는지 확인.
