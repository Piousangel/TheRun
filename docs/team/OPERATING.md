## 0-1. 생산성 기준 (오너 피드백 11-16: "그닥 생산성 있는 작업을 한 것 같지 않다")
지난 며칠 동안의 진단: 실행 한 번에 작은 수정 1개, 회의록은 길고 반영은 짧았다. 매일 '측정 불가'로 넘어갔고, 목표를 사용자가 체감하는 결과가 아니라 작업 단위로 잡았다. 아래를 지킨다.

1. **주간 목표는 숫자 1개** (월요일 회고에서 정하고 direction.md 맨 위에 쓴다)
   - 예시: launch.md 스프린트 칸 완료 수(모바일·데스크톱 둘 다 완료 기준), e2e 시나리오 수
   - 매일 회의 첫 줄에 '주간 목표 진행: 지난주 대비 +N'을 쓴다. 숫자를 볼 수 없으면 측정 장치부터 만드는 게 그날의 반영이다.
2. **하루 산출 기준**: 실행마다 **사용자가 체감하는 변화 1개 이상**을 머지·배포한다.
   - 문서만 있는 PR은 반영으로 치지 않는다(월요일 스펙·회고 제외).
   - 메인 작업을 머지하고 시간이 남으면 **다음 백로그 항목을 이어서** 한다. 한 세션에 2~3개 PR도 좋다. 작은 수정(오타, 깨진 링크, 문구)은 모아서 한 PR로 처리한다.
3. **회의는 짧게**: 회의록은 40줄 이내로 쓴다. 역할 발언은 근거 있는 한 줄씩. 시간을 쓰는 곳은 회의가 아니라 만드는 일이다.
4. **임팩트 우선순위**: 후보 표에 '주간 목표에 주는 효과'를 쓰고, 그 효과가 가장 큰 것을 고른다. 안전하고 작은 일만 고르는 쏠림을 리뷰어가 막는다. 사흘 연속 소형 수정만 했으면 넷째 날은 반드시 큰 항목을 한다.
5. **증거**: PR마다 전후 스크린샷(화면 변경 시)과 '이 변화로 기대하는 숫자 변화'를 한 줄 쓴다. 다음 회고에서 실제 숫자와 비교한다.
6. **보고 메일 첫 줄**은 '어제보다 나아진 점: <사용자가 체감하는 변화 한 줄>'로 쓴다. 쓸 게 없으면 그날은 실패한 날이다. 이유와 내일 만회할 계획을 쓴다.
7. **11-17 회의의 첫 안건**은 '지난 며칠 생산성 회고'다. 위 진단에 동의하는지, 무엇을 바꿀지 3줄로 쓰고, 이번 주 숫자 목표를 정한다(월요일 회고를 대신한다).

## 2. 역할 (회의록 docs/team/meetings/YYYY-MM-DD.md)
맨 위에 **어제 회고**를 쓴다: 어제 반영이 실제로 어땠나(CI·배포·화면 확인), 잘된 점, 부족한 점, 다음에 다르게 할 것 각 1줄.
- **클럽 운영자(PO 관점)**: "이번 주 금요일 경기를 이 앱으로 운영할 수 있나?"를 매일 묻는다. 주간 루프에서 막히는 지점을 짚는다.
- **PM**: launch.md 진행률, 남은 항목 중 오늘 할 후보 3~5개를 표로 정리한다(효과 / 비용 / 런칭 기여 / 오늘 가능?).
- **개발 리드**: 구조·FSD 경계·데이터 계약(포트/어댑터) 관점의 위험을 본다.
- **디자이너**: `DESIGN_SYSTEM.md`와 UI 개편 스펙 기준으로 모바일(390×844)과 데스크톱 첫 화면을 확인한다.
- **QA**: CI(lint·type-check·test·build·e2e) 상태, 최근 배포본 상태를 확인한다. 실사이트에 접근할 수 없으면 데모(local) 모드 로컬 빌드로 확인하고, 그 사실을 적는다.
- **리뷰어**: 후보마다 반론 한 줄을 쓰고 오늘 할 1개를 고른다. 못 고른 건 backlog로 보낸다.

## 4. 반영과 머지 (오너 결정: CI 통과 시 자동 머지)
- 브랜치 `daily/YYYY-MM-DD-<주제>` → 구현 → 로컬 검증 `pnpm lint && pnpm type-check && pnpm test && pnpm build` → PR.
- PR의 GitHub Actions CI(e2e 포함)가 **전부 초록이 된 뒤에만** main에 머지한다(squash). 하나라도 실패하면 머지하지 않는다. PR에 원인을 적고 열어 둔다.
- main 머지는 Vercel 운영 배포다. 머지 뒤 배포 URL이 200인지 확인한다.
- 기록: `docs/daily/log.md` 한 줄, backlog·launch.md 갱신, 갈림길이면 `docs/product-decisions.md`에 '팀 판단'으로 기록한다. 회의록도 같은 PR에 넣는다.

## 4-1. 모바일·데스크톱 2벌 병렬 (오너 결정 11-16, D-18)
**모든 화면 작업은 모바일과 데스크톱을 같은 PR에서 함께 완성한다.** "모바일 먼저, 데스크톱은 나중에"는 금지다.
- 기준 화면: 모바일 390×844(하단 탭바·헤더), 데스크톱 1280×800(사이드바·상단바). UI 개편 스펙 A-2(셸)를 따른다. 768~1279px 중간 폭도 깨지지 않아야 한다.
- 같은 기능이라도 **화면 구성은 기기에 맞게 다르게** 한다. 데스크톱이 모바일을 늘린 화면이면 안 된다.
  - 데스크톱: 목록+상세 2단, 넓은 표, 키보드 조작, 드래프트 보드·순위표처럼 한눈에 많이 보는 화면
  - 모바일: 한 손·엄지, 하단 액션, 시트(URL 상태)
  - 예: 경기 당일 기록은 모바일이 주 사용 환경이지만, 데스크톱에서도 기록·수정할 수 있어야 한다(운영진 사후 정리). 드래프트는 데스크톱이 보드형, 모바일은 내 차례 중심.
- **완료 조건**(PR에 체크리스트로):
  1. e2e: 새 화면의 시나리오가 `mobile`·`desktop` 두 프로젝트에서 모두 통과한다(playwright.config.ts에 이미 둘 다 있다. 한쪽에서만 skip 금지)
  2. 스크린샷: PR 본문에 모바일·데스크톱 캡처를 1장씩 이상 첨부한다(e2e `visual/` 또는 로컬 캡처)
  3. 뒤로가기·새로고침·딥링크가 두 기기에서 같은 화면을 복원한다
  4. 터치 타깃 44px(모바일), 키보드 포커스·단축키(데스크톱)
- 스프린트 표(launch.md)의 모든 칸은 두 기기 완료를 기준으로 체크한다.

## 5. DB (오너 결정: 적용까지 팀에 맡김)
- 스키마 변경은 `supabase/migrations/`에 새 파일로만 추가한다. 이미 적용된 파일은 고치지 않는다.
- 적용은 사람 손이 아니라 워크플로가 한다(launch.md B의 '마이그레이션 적용 워크플로'). 한 파일 = 한 트랜잭션(`psql -1`), 적용 기록 테이블, 실패하면 중단.
- **절대 금지**
  - 조건 없는 UPDATE/DELETE, DROP TABLE/COLUMN, TRUNCATE를 운영 DB에 적용하는 것
  - 역할(role) 일괄 변경
  - 백업 없이 데이터 이동
  - 위가 필요하면 PR만 열고 메일로 사람 확인을 받는다. 2026-03 '전원 관리자 승격' 사고가 있었다(`docs/supabase-reconnect.md`).
- 서비스 롤 키·DB URL은 GitHub 시크릿에만 있다. 코드·로그·회의록에 쓰지 않는다.
